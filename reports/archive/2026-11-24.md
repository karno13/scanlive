**Data weryfikacji:** 24 listopada 2026, ok. 08:20 CET  
**Gałąź / commit bazowy:** `main` / `47aaaa0b21242ab303e7747644ba136414919e52`  
**Zakres:** repozytorium GitHub, dokumentacja, historia commitów, Issues/PR-y, GitHub Actions, publiczny research źródeł ofert i bibliografii.  
**Ograniczenia:** nie mam dostępu do lokalnej bazy właściciela ani do bieżącego katalogu ofert BookFlip. Nie uruchamiałem aplikacji, testów ani skanowania sieciowego. Liczby pochodzące z wcześniejszej kopii bazy są oznaczone jako historyczne.

> Raport jest materiałem analitycznym dla właściciela i Claude Code. Nie jest zgodą na implementację. Nie wykonano żadnych zmian poza publikacją plików w `reports/`.

## Wnioski w skrócie

1. **Błąd Node 22.16 ma mocne, konkretne wyjaśnienie upstream.** Kod BookFlip używa numerowanego parametru SQLite `?1` i wiąże go pozycyjnym argumentem. Problem Node.js z takim wiązaniem został naprawiony upstream, a poprawka weszła do Node 22.20.0. To tłumaczy, dlaczego Node 24 przechodzi, a dokładnie testowana wersja 22.16 nie.
2. **Macierz CI nie daje obecnie wyniku Windows.** Domyślne `fail-fast: true` zatrzymuje pozostałe zadania po pierwszym błędzie. W ostatnim przebiegu zadania Windows zostały anulowane, zanim uruchomiły testy.
3. **42 podejrzane przypisania ISBN nadal wymagają audytu na świeżej kopii bazy.** To historyczny wynik dla 2605 automatycznych przypisań, nie aktualny pomiar.
4. **Nie znalazłem nowego źródła ofert gotowego do legalnej i sensownej integracji.** Antykwariat.biz.pl jest nowym tropem, ale ma tylko trzy widoczne ogłoszenia i niekompletny regulamin.
5. W bibliografii znalazłem osiem nowych lub świeżo istotnych polskich wydań z potwierdzonym ISBN, w tym powieść ze świata Baldur’s Gate 3.

**Najlepsza kolejność przy ograniczonym czasie:** usunąć niezgodność `?1` z Node 22.16, uzyskać pełny wynik macierzy Windows/Linux, a następnie sklasyfikować podejrzane przypisania. Nowe adaptery mają niższy priorytet.

### A4. Przyczyna błędu Node 22.16 — mocniejszy dowód niż w poprzednim raporcie

W [shipping-backfill.mjs](https://github.com/karno13/scanlive/blob/main/shipping-backfill.mjs) przygotowane zapytanie `untouchable` używa `?1` trzy razy, a wywołanie przekazuje jeden argument pozycyjny: `untouchable.get(offer.id)`.

To pasuje do znanego błędu `node:sqlite`:

- [Node.js issue #59340](https://github.com/nodejs/node/issues/59340) opisuje, że wówczas `?NNN` było traktowane jak parametr nazwany, a przekazanie wartości pozycyjnie kończyło się dokładnie błędem „column index out of range”.
- [PR #59350](https://github.com/nodejs/node/pull/59350) naprawił obsługę `?NNN` jako parametrów pozycyjnych.
- Poprawka jest wymieniona w [release notes Node 22.20.0](https://nodejs.org/en/blog/release/v22.20.0).

**Wniosek:** najbardziej prawdopodobna przyczyna testu 634 to użycie `?1` w kodzie uruchamianym na Node 22.16, czyli wersji sprzed backportu poprawki. To bardzo mocny trop, nie dowód wykonania poprawki w BookFlip — nie uruchamiałem testu.

Najmniej ryzykowny sposób zachowania deklarowanej zgodności z Node 22.16 to zamienić trzy wystąpienia `?1` na trzy zwykłe `?` i przekazać ten sam identyfikator trzy razy. Alternatywą jest podniesienie minimalnej wersji Node 22 do 22.20, ale wymagałoby to zmiany deklaracji w `package.json`, README i macierzy CI. Nie rekomenduję cichego porzucenia 22.16 bez decyzji właściciela.

### 1. Usunąć niezgodność `?1` z Node 22.16

<badge>WARTA TESTU</badge>

- **Problem:** wspierana przez README i `package.json` wersja Node 22.16 nie przechodzi testu naprawy kosztów dostawy.

- **Proponowany zakres:** zastąpić numerowany parametr trzema zwykłymi `?` i przekazać `offer.id` trzy razy. Nie zmieniać logiki warunku ani transakcji.
- **Pliki do sprawdzenia:** `shipping-backfill.mjs`, `test/shipping-backfill.test.mjs`, `.github/workflows/scanner-tests.yml`.
- **Korzyść:** zachowanie deklarowanej zgodności z Node 22.16 bez dodatkowej zależności i bez wymuszania aktualizacji środowiska użytkownika.
- **Trudność:** 1/5. **Wartość:** 5/5. **Pewność dowodów:** 5/5.
- **Ryzyko:** niskie; trzeba potwierdzić, że identyfikator jest wiązany we wszystkich trzech warunkach.
- **Zgodność z kierunkiem:** bardzo wysoka, P0.

**Kryteria akceptacji:**
1. Test naprawy przechodzi na Node 22.16.0 i Node 24.
2. Oferta z przypisaniem ręcznym pozostaje nietknięta.
3. Zestaw pozostaje nietknięty.
4. Automatyczna oferta obcojęzyczna nadal jest ponownie identyfikowana.
5. Nie ma migracji schematu i nie dotyka się aktywnej bazy właściciela.

**Hipoteza:** co najmniej 75% pozycji oznaczonych przez obecną regułę jako podejrzane przypisanie to rzeczywiste błędy ISBN/edycji albo błędne przypisanie zestawu do pojedynczego tomu.

**Przebieg:**
1. Na kopii najnowszej bazy wygenerować aktualną listę konfliktów.
2. Każdą pozycję ręcznie oznaczyć: rzeczywisty błąd, prawidłowy alias/zapis tytułu, zestaw/wariant albo niejednoznaczne.
3. Dla każdej etykiety zapisać krótki powód i źródło dowodu (tytuł, autor, ISBN, zdjęcie/opis oferty).
4. Nie przepinać żadnej oferty w ramach eksperymentu.

**Miernik:** precyzja reguły = liczba rzeczywistych błędów / liczba wszystkich oflagowanych pozycji. Osobno policzyć fałszywe alarmy dla zestawów i aliasów.

**Warunek decyzji:** jeśli precyzja wyniesie co najmniej 75%, utrzymać regułę i dodać przykłady do testów; jeśli będzie niższa, najpierw poprawić klasyfikację wyjątków. Nie zmieniać progu na podstawie samej liczby 42.

**Naprawić test 634 na Node 22.16, zachowując wsparcie tej wersji.**

**Dlaczego właśnie to:** problem jest odtwarzalny, ma mocne wyjaśnienie w upstream Node.js i dotyczy wersji deklarowanej jako wspierana. Koszt naprawy jest mały, a wynik odblokowuje wiarygodną ocenę Windows.

## G. Czego nie robić

- **Nie dodawać teraz adaptera Antykwariat.biz.pl.** Trzy oferty, brak API i niekompletny regulamin nie uzasadniają kosztu ani ryzyka.
- **Nie przepinać automatycznie podejrzanych przypisań.** 42 pozycje to sygnał do audytu, nie lista błędów do masowej naprawy.
- **Nie podnosić minimalnej wersji Node bez decyzji właściciela.** Prostsza poprawka zapytania może zachować wsparcie 22.16.
- **Nie traktować anulowanych zadań Windows jako zaliczonych.** Wymagają własnego wyniku.
- **Nie traktować awarii instalacji Chromium jako regresji UI.** Właściwy browser smoke nie wystartował.
- **Nie uruchamiać lokalnego zespołu agentów bez nadzoru ani autostartu.** Dokumentacja przewiduje pilotaż 5–10 cykli; najpierw trzeba zebrać wyniki.
- **Nie dodawać kolejnych ogólnych fraz skanowania bez pomiaru.** `query-yield.mjs` już istnieje; należy korzystać z jego wyników zamiast rozbudowywać listy na wyczucie.
- **Nie dodawać chmury, nowych zależności produkcyjnych ani przebudowy frameworkowej.** Nie rozwiązują aktualnych problemów.

## Odpowiedź: co najbardziej poprawi BookFlip w najbliższych miesiącach?

1. **Niezawodność na wspieranych wersjach Node i Windows** — bez tego każda kolejna funkcja zwiększa ryzyko.
2. **Wysoka precyzja przypisań ISBN i wydań** — błędnie rozpoznana książka podważa katalog, kolejkę i wycenę.
3. **Dopiero potem nowe źródła ofert** — większy wolumen jest użyteczny tylko wtedy, gdy dane są legalnie pobierane i poprawnie rozpoznawane.

Najbardziej opłacalna praca teraz to nie „więcej ofert”, lecz **mniej błędów identyfikacji i pełny, wiarygodny test na Windows**.
