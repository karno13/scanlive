## E. Eksperyment: czy wyszukiwanie po ISBN realnie uzupełnia wyniki tytułowe?

**Hipoteza:** dla 10 powyższych wydań z 2025–2026 r. wyszukiwanie istniejącym mechanizmem ISBN na Vinted znajdzie co najmniej 10% dodatkowych, poprawnych ofert względem wyszukiwania tytuł + autor, przy odsetku fałszywych trafień poniżej 5%.

**Metoda:**
1. Wybrać 10 ISBN-ów z sekcji D, po sprawdzeniu, które istnieją już w katalogu.
2. Na kopii bazy wykonać istniejące wyszukiwanie tytuł + autor oraz istniejące wyszukiwanie po ISBN.
3. Ręcznie oznaczyć wyniki: prawidłowa edycja, inne wydanie, inna książka, duplikat.
4. Porównać liczbę unikalnych poprawnych ofert i fałszywych trafień.

**Próg decyzji:**
- wynik pozytywny: ≥10% dodatkowych poprawnych ofert i <5% fałszywych trafień;
- wynik negatywny: <5% dodatkowych ofert albo >5% fałszywych trafień;
- 5–10%: brak decyzji, powtórzyć na kolejnej próbce.

Nie dodawać nowego harmonogramu ani nowych żądań. Eksperyment wykorzystuje istniejące mechanizmy i kopię bazy. Nie traktować braku ofert jako dowodu braku popytu.

## F. Jeden najlepszy następny krok — audyt image-cache

**Dlaczego ten krok pierwszy:** dotyczy publicznego repozytorium i potencjalnie danych użytkownika. Błąd w katalogu lub skanerze można poprawić później; raz opublikowane obrazy mogą pozostać w historii Git nawet po usunięciu z bieżącego drzewa.

**Specyfikacja dla Claude Code (materiał analityczny, nie automatyczne polecenie):**

1. Na lokalnej kopii repo sprawdzić 114 śledzonych ścieżek data/image-cache, rozmiary i metadane plików.
2. W kontrolowanym środowisku właściciela ustalić pochodzenie próbek obrazów: okładki, zdjęcia ofert, zdjęcia egzemplarzy lub inne.
3. Sprawdzić, czy katalog cache jest wyprowadzany z lokalizacji bazy, i czy może wskazać katalog repozytorium przy ustawieniu BOOKFLIP_CATALOG_DB.
4. Jeżeli cache jest wyłącznie odtwarzalny, zaproponować wykluczenie data/image-cache w .gitignore i usunięcie go z bieżącego drzewa.
5. Osobno przedstawić konsekwencje czyszczenia historii Git. Nie przepisywać historii bez osobnej zgody właściciela.

**Kryteria akceptacji:**
- potwierdzone pochodzenie i klasyfikacja cache;
- brak śledzonych plików cache w docelowym repo;
- nowy cache trafia do katalogu danych użytkownika;
- test na świeżym klonie nie zapisuje plików cache w repo;
- żadna baza, historia ofert ani ręczne decyzje nie są modyfikowane.

**Plan testów:**
- test jednostkowy lokalizacji cache w katalogu tymczasowym;
- sprawdzenie git ls-files data/image-cache;
- sprawdzenie git check-ignore dla przykładowego pliku;
- uruchomienie aplikacji na pustej, izolowanej bazie;
- porównanie git status przed i po uruchomieniu.

**Warunek przerwania:** jeśli nie da się ustalić pochodzenia zdjęć albo cache zawiera dane, których nie można bezpiecznie usunąć, zatrzymać się i przedstawić właścicielowi listę ryzyk. Nie czyścić historii automatycznie.

## G. Czego nie robić teraz

1. **Nie dodawać Vivarium ani Kwadrygi bez zgody na automatyczny odczyt.** Sam fakt, że strona jest publiczna, nie daje licencji na pobieranie katalogu.
2. **Nie dodawać Bookway ponownie.** Adapter kategorii już istnieje.
3. **Nie skanować Bookbot przez wyszukiwarkę ani filtry.** Dokumentacja źródeł wskazuje, że te ścieżki są zakazane przez robots.txt; dozwolone strony wydawców i sitemap nie tworzą automatycznie kompletnej wyszukiwarki.
4. **Nie uruchamiać ręcznego workflow z Allegro i nie używać local-scan --source all przed domknięciem bramki prawnej.** Główna ścieżka UI ma filtr, ale alternatywne wejścia go omijają.
5. **Nie traktować rzadkości książki jako dowodu rentowności.** Do tego potrzebne są realne ceny sprzedaży, czas obrotu i stan egzemplarza.
6. **Nie rozbudowywać teraz modułu zysku, alertów, kosztów i handlu.** Priorytet pozostaje skaner, katalog, weryfikacja.
7. **Nie dodawać frameworka, chmury, kont ani nowych zależności produkcyjnych.** Obecna architektura Node + SQLite jest wystarczająca dla jednej osoby.
8. **Nie usuwać image-cache ani nie przepisywać historii Git bez audytu i decyzji właściciela.** Potencjalny problem prywatności nie uzasadnia ryzykownego, automatycznego kasowania danych.
